# SAI-CRM — Functional & Administrative Hierarchy Master (Stage 2)
**Requirements and implementation baseline — 4 November 2026**

## Purpose
Configure how organizational **roles may report to other roles** in Administrative and Functional hierarchies. This master defines policy/structure; it DOES NOT assign named employees to managers and DOES NOT automatically grant CRM permissions.

## Confirmed relationships
- Business Line, Country, Region, Branch, Department and Organizational Role Masters are canonical sources.
- Organizational Role has `Central`, `Branch`, `Both` applicability.
- This master is separate from the existing User Master, CRM Permission Role and Role & Permission Matrix.
- Administrative manager is distinct from functional manager. Person-to-person, effective-dated assignments are deferred to Employee Master.
- Maintain Business Lines UI/UX standard, Super Admin-only configuration, full audit and safe state transitions.
- Production Database remains version 12 until this stage is tested and released.

## Terminology
- **Reporting Rule**: a permitted directed relationship, *Child Organizational Role → Parent Organizational Role*.
- **Administrative**: normal line-management chain for an organizational scope.
- **Functional**: specialist/departmental oversight; does not replace the administrative manager.
- **Scope**: where the rule is valid. `Global`, `Business Line`, `Region`, `Branch`, `Department` (Department refers to Central/Branch Department catalog identity).
- **Active**: eligible for future Employee Mapping. Inactive/Archived/Deleted retained for audit.

## Rules — HIER-FR
- **HIER-FR-001:** Only an approved, verified Super Admin can list, create, edit, activate/inactivate, archive, restore and logically delete rules, with enforcement on the server.
- **HIER-FR-002:** Rule type must be exactly `Administrative` or `Functional`; system ID format is `HR-001` etc., immutable and generated by DB.
- **HIER-FR-003:** Parent and Child must be distinct, existing **Active Organizational Roles**, and each must be compatible with the rule's selected Central/Branch applicability.
- **HIER-FR-004:** A rule must choose Scope Level (`Global`, `Business Line`, `Region`, `Branch`, or `Department`). For non-Global scope, Scope Record is mandatory and must reference a currently Active record in the corresponding master. Scope may not cross business-line boundaries via unrelated Branch/Region records.
- **HIER-FR-005:** Administrative hierarchy permits **at most one active parent per Child Role within an exact scope**. Functional hierarchy permits multiple parents to support matrix oversight, subject to cycle controls. A child can have different configured parents in different scopes.
- **HIER-FR-006:** No self-reporting or directed cycles may be created or reactivated within the same rule type and scope. Validate on the server within the write transaction; database uniqueness protects exact duplicates.
- **HIER-FR-007:** A future employee's actual reporting manager(s) must be explicitly mapped and effective-dated in Employee Mapping. These rules only constrain eligible assignments; do not infer a specific person's manager from Role Master alone.
- **HIER-FR-008:** A change to a Reporting Rule must not modify employee records, lead owners, existing user scopes, permission roles or operational records.
- **HIER-FR-009:** Status lifecycle follows `Active ↔ Inactive → Archived → Deleted` with permitted restoration to eligible prior states; deletion is logical only, with required reason for transitions, optimistic version and append-only audit.
- **HIER-FR-010:** Modification of role/scope/type on an existing rule is restricted; change these by inactivating the old rule and creating a new one. This preserves the meaning of historical configuration.
- **HIER-FR-011:** Records/Overview/Tree views use filtered data; tree shows distinct rule types and context, with no false empty hierarchy when a parent is filtered out. Counts reconcile to list scope and filters.
- **HIER-FR-012:** List supports search, type, status, Scope Level, page-size, default Last Modified descending. A permitted rule is not a permission grant.
- **HIER-FR-013:** Audit events must include actor, timestamp, old/new status or field values, reason, and linked rule ID. No physical deletions of rules or audit events.
- **HIER-FR-014:** Any rule that conflicts with future active employee-manager assignments must be prevented from deactivation or deletion once Employee Master is integrated. Until then, there are no employee links to migrate.
- **HIER-FR-015:** All write operations must use the established request transaction and be isolated from existing user/role permissions.

## Initial module fields
| Field | Required | Rules |
|---|---|---|
| System ID | Auto | HR-001, immutable |
| Hierarchy Type | Yes | Administrative / Functional |
| Parent Organizational Role | Yes | Active Organizational Role |
| Child Organizational Role | Yes | Active Organizational Role, not self |
| Scope Level | Yes | Global / Business Line / Region / Branch / Department |

| Created/Modified metadata | Auto | Actor, timestamps, optimistic version |

## Important reporting constraint
A role-based relation such as **Sales Executive → Branch Manager** is a configurable *permitted reporting pattern*. It does not imply all Sales Executives report to the same Branch Manager person, nor that the manager can view all records automatically.

## Technical scope
- Additive migration 013; `reporting_hierarchy_rules`, `reporting_hierarchy_events`, `reporting_hierarchy_sequence_v13`.
- Existing Organizational Role Master is prerequisite. Do not modify employee/user permissions.
- Read/write API with scoped reference validation, cycle detection and audit.
- Business Lines-style master UI and browser/real-Postgres acceptance tests.

## Acceptance criteria
- AC-01: ordinary user receives 403 for read and write; Super Admin can configure rules.
- AC-02: Role A cannot report to itself; A→B, B→C then C→A fails within same type/scope.
- AC-03: second Active Administrative parent for one Child and exact scope fails.
- AC-04: two distinct Functional parents for same Child are allowed unless a cycle would result.
- AC-05: Role applicability matches Central/Branch scope; inactive or archived Role cannot be selected.
- AC-06: Scope Record belongs to canonical active master, else reject with meaningful validation.
- AC-07: deactivation, archiving, restoration and logical deletion follow lifecycle and audit/version rules.
- AC-08: SQL version 013 applies atomically on isolated test DB, previous versions and data unaffected.
- AC-09: Records, Overview and hierarchy graph reconcile; no unauthenticated access.
- AC-10: no existing `users`, `user_scopes`, Department or Organizational Role records are changed by a hierarchy configuration write.

## Deferred to Employee Master
- Actual named employees' administrative manager, additional functional managers, primary vs secondary relationships, effective dating and historical branch transfers.
- Handling cross-scope managerial exceptions with explicit approval workflows.
- Reporting-based data visibility and permission escalation.
